# Режимы подбора и карта

Интерфейс начинает с режима **«Без известных препятствий»** (`explore`). Он оставляет варианты, для которых пока не подтверждены вместимость или обязательные пожелания. Такой допуск отмечается `provisional: true`: условие ещё нужно уточнить. Установленное несоответствие обязательному требованию и конфликт источников исключают вариант в обоих режимах.

Режим **«Только подтверждённые»** (`verified`) требует положительных сведений о вместимости и каждом обязательном условии. Это допуск по имеющимся источникам, а не гарантия на месте или подтверждение свободного номера. Заявление владельца сохраняет свою маркировку и не превращается в независимую проверку.

Желательные условия влияют на порядок вариантов. Их невыполнение не исключает номер. В фильтрах пожелание можно сделать обязательным. Подтверждённые допуски располагаются перед предварительными.

| Обязательное условие | `verified` | `explore` |
| --- | --- | --- |
| Выполнено по источнику | Допуск | Допуск |
| Не выполнено | Исключение | Исключение |
| Нет данных или сведения устарели | Исключение | Предварительный допуск |
| Источники противоречат друг другу | Исключение | Исключение |

Без данных о безопасности нельзя утверждать «безопасно». Аналогично, отсутствие измерений не подтверждает тишину или чистый воздух. Режим поиска меняет допуск кандидата, а не факты о нём: `evidenceStatus`, `assumed` и объяснения сохраняются. Помощник получает тот же допуск и предупреждения.

## API

В запросы `/api/search`, `/api/hotels/:id/evaluate` и поездку помощника можно передать `admissionMode: "explore"` или `"verified"`. Если поле отсутствует, API сохраняет прежнее поведение `verified` для совместимости. Интерфейс задаёт `explore` явно и хранит выбор вместе с поездкой.

У каждой оценки номера и кандидата помощника есть `provisional`. Оно истинно только тогда, когда допуск зависит от неизвестного или устаревшего обязательного условия либо неизвестной вместимости. Неизвестное желательное условие само по себе не делает допуск предварительным; оно всё равно остаётся неизвестным в списке критериев.

## Карта

Основная карта использует Leaflet и обычные растровые тайлы OpenStreetMap. У неё есть подписи мест и улиц, масштаб, управление с клавиатуры, обзор результатов и маршрут выбранного отеля. На карту попадают все результаты с известными координатами, независимо от числа загруженных карточек.

Сетевая подложка требует интернета. Сохранённая в проекте схема служит запасным вариантом и не загружает тайлы для офлайн-хранения. Подписи OSM и ссылки на атрибуцию остаются видимыми. Политика сервиса: <https://operations.osmfoundation.org/policies/tiles/>.

Маршрут и его длина по-прежнему рассчитаны по сохранённому графу; онлайн-подложка не делает их свежей навигацией. Входы и соединительные участки приблизительны, отсутствие лестниц на карте не подтверждает доступность с коляской.

## Расширенная проверка

После сборки запустить `scripts/verify-http-integration.py --keep-running` на свободных локальных портах. Затем передать адреса основного и лабораторного серверов:

```powershell
python -X utf8 scripts/verify-search-modes.py --app http://127.0.0.1:8090 --lab http://127.0.0.1:8091
```

Проверка сравнивает оба режима, исходные статусы доказательств, сочетания обязательных фильтров, вместимость, сортировку, детали отеля и рекомендации помощника. Отчёт по умолчанию сохраняется в игнорируемую `.local/`. Синтетические случаи конфликта и несоответствия проверяются отдельно от 96 реальных объектов.
