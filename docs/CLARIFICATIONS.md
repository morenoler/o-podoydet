# Уточнения, которые меняют подбор

Путешественник может выяснить неизвестное условие конкретного объявления, получить ответ владельца и повторить поиск с теми же датами и гостями. Ответ участвует в новой выдаче как **заявление владельца**. Независимой проверки помещения это не заменяет.

## Сценарий

1. В карточке опубликованного объявления задайте поездку и откройте «Подготовить личный вопрос».
2. Выберите семейное размещение, окна во двор или путь до номера без ступеней. Проверьте вопрос, обязательность условия и даты. Необязательное личное дополнение видит только владелец объявления.
3. В кабинете владельца откройте «Вопросы гостей → Уточнения для подбора». Укажите «Да», «Нет» или «Пока не знаю», пояснение и известную дату проверки. Если ответ относится только к части номеров либо зависит от неустановленных условий, выбирайте неизвестность.
4. Проверьте область действия и срок перепроверки перед сохранением. Противоположные заявления из разных диалогов сохраняются как конфликт; владелец явно отмечает исправляемые сведения.
5. Путешественник видит ответ в собственном кабинете и нажимает «Пересчитать подбор». Запускается новый поиск. Старые результаты и разбор помощника сохраняют свой снимок доказательств.

Реальные гостиницы исследовательского каталога не связаны с кабинетами владельцев. Для них доступен черновик вопроса о выбранной категории и копирование текста. Приложение не отправляет его во внешние каналы.

## Область действия и достоверность

`listing_unit` означает вариант размещения, описанный одним объявлением. Это не подтверждённый физический номер реального отеля. Условия разных объявлений не объединяются в один подходящий вариант. Вместимость, этаж и направления окон проверяются отдельно.

Владелец может уточнять только `family`, `courtyard`, `step_free_access`. Его ответ не подтверждает безопасность района, чистоту воздуха, внешний шум или весь маршрут до пляжа. Обычные публичные вопросы `account_questions` также не превращаются в факты.

Публичная выдача содержит `reportedEvidence`: условие, значение, область действия, время записи, известную дату наблюдения, применимые даты, срок перепроверки, `method=owner_response` и `provenanceStatus=reported`. Текст вопроса, пояснение владельца, личное дополнение, идентификатор диалога и личности путешественника в эту проекцию не входят. Полный исходный запрос возвращается только его автору; владелец получает даты, количество гостей и явно отправленное дополнение.

Ответы не перезаписываются: каждая версия сохраняется в истории. Новая версия одного диалога заменяет предыдущую; сведения из других диалогов заменяются только через явный `supersedes`. Неизвестный ответ не оживляет прежнее положительное заявление. Противоположные ответы нельзя разрешить одним более новым временем записи или истечением срока.

Положительное заявление должно покрывать все даты поездки. Отрицательное ограничение учитывается при любом пересечении с поездкой. Дата выезда включена: путь из номера и правила размещения важны и в день выезда. Условия вне применимых дат не считаются подтверждением. Дата наблюдения в будущем запрещена. Если она неизвестна, `observedOn=null`; время записи не выдаётся за наблюдение. Срок перепроверки — от 1 до 90 дней, считается от известной даты наблюдения либо даты записи по времени Пусана.

Изменение города, адреса, типа размещения, вместимости, этажа или сторон окон навсегда инвалидирует старую область действия. Возврат прежнего текста объявления не восстанавливает старые ответы. Изменение названия или фотографий само по себе этого не делает.

Сервер отвергает распознанные противоречия между выбранным значением и пояснением, например «Да, без ступеней» вместе с явным сообщением о ступенях без обхода. Это ограниченная проверка формулировок, а не гарантия понимания любого свободного текста.

## API

Все маршруты требуют штатную сессию кабинета; чужой владелец получает `404`, неверная роль — `403`.

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/listings/:id/clarifications` | Личное уточнение путешественника; ответ `201` |
| `GET /api/account/clarifications` | Собственные диалоги путешественника |
| `GET /api/host/clarifications` | Диалоги объявлений текущего владельца |
| `POST /api/host/clarifications/:id/answers` | Новая версия ответа; ответ `200` |
| `POST /api/hotels/account-listing:<listingId>/evaluate` | Текущая оценка объявления и всех восьми условий |

Типы запросов и ответов находятся в `shared/clarifications.ts`. Запись использует `requestKey`; повтор того же ключа и содержания не создаёт дубликат. Другое содержание с тем же ключом даёт `409`. Ответ также требует `expectedVersion`: конкурирующие редакторы не затирают изменения друг друга. Проверка владельца, версии, области действия, запись ответа и замена сведений проходят в одной транзакции.

`scopeChanged` и `evidenceStatus` в личном диалоге показывают текущую применимость и совокупный результат по исходной поездке. Это отличается от наличия ответа: отвеченный вопрос может по-прежнему требовать внимания.

## Проверка

```powershell
npm run backend:test
npm test
npm run backend:build
python -X utf8 scripts/verify-clarifications-integration.py --port 8084
```

HTTP-проверка создаёт отдельную временную схему PostgreSQL и вымышленные аккаунты, выполняет запросы через API, проверяет перезапуск и останавливает свой сервер. Используется Docker либо явно настроенная тестовая PostgreSQL. Отчёт и временные файлы остаются в игнорируемой `.local/`. Пользовательская демонстрационная база не используется. Проверяются приватность, история, повторные запросы, конкуренция, совместимость условий в одном варианте, сроки, применимые даты, конфликты и изменения объявления.
