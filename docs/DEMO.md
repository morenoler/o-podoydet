# Локальная демонстрация кабинетов

`data/demo/preview.sqlite3` — исходный SQLite-образец для явного импорта в отдельную схему PostgreSQL, созданный с нуля из `data/demo/fixtures.json`. Все люди, адреса, объекты, цены, поездки и вопросы вымышлены. База не копировалась из основной или лабораторной версии.

Для запуска нужны Node.js 24+, Java 21, Maven 3.9+ и PostgreSQL 16 (Docker Desktop или собственный `DATABASE_URL`). Сервер использует Spring Boot 3.5.6; рабочая база — PostgreSQL. Python 3.11+ нужен для помощника; обычный подбор и кабинеты работают без него.

```powershell
npm ci
npm run build:all
npm run demo:setup
npm run demo:start
```

Откройте `http://127.0.0.1:8082`. Учебные аккаунты:

- Путешественник: `user@demo.test`, пароль `UserDemo2026!`.
- Отельер: `host@demo.test`, пароль `HostDemo2026!`.

Это публичные демонстрационные пароли. Используйте базу только локально. Она не предназначена для реальных персональных данных или публичного сервиса.

`demo:setup` проверяет целостность исходной базы и создаёт новую копию `.local/demo.sqlite3`. Даты только в этой копии сдвигаются относительно дня установки по Пусану: ожидающие и подтверждённые поездки остаются будущими, завершённые — прошедшими. Исходный файл в `data/demo/` не меняется. Если целевой файл или его SQLite sidecar уже существует, установка завершается ошибкой без перезаписи. Повторно запускать установку перед каждым стартом не нужно.

`demo:start` использует основную frontend-сборку `dist/`, включает кабинеты и выключает лабораторный режим. Порт задаётся через `DEMO_PORT`, по умолчанию `8082`. При первом старте скрипт явно задаёт `LEGACY_DB_PATH=.local/demo.sqlite3` и переносит образец в схему PostgreSQL `demo` (`DEMO_DB_SCHEMA`). Все последующие изменения кабинетов и история помощника сохраняются в PostgreSQL; SQLite остаётся исходным образцом. Повторный импорт не перезаписывает существующие строки. Новые загруженные фотографии находятся в `.local/demo-uploads/`. Схема демо должна отличаться от основной `DB_SCHEMA`; загрузки основной и лабораторной копий не используются. Скрипт отключает платный разбор текста через `LLM_API_KEY`; локальный помощник Ollama при наличии настройки остаётся доступен. Остановка: `Ctrl+C` в терминале запуска.

При первом старте сервер отдельно импортирует обычный проверенный каталог Пусана из `data/verified-hotels.json`. Три учебных опубликованных объявления видны с префиксом «ДЕМО» и пояснением о вымышленных данных. Они не получают чужие фотографии, координаты или маршруты.

## Что входит в базу

- Два аккаунта, по одному на каждую роль; телефоны пустые, адреса почты используют домен `.test`.
- Четыре объявления: три опубликованных и один черновик. У каждого есть этаж, направления окон и закрытая заметка для поиска.
- Шесть заявок: две ожидающие, одна подтверждённая, одна отменённая и две завершённые. Историческая стоимость завершённых поездок отличается от текущей цены объявления.
- Шесть вопросов: три открытых и три с ответом отельера.
- Ноль сессий, загрузок, поисковых историй и запусков помощника. Таблицы старых вопросов и черновиков также пусты.

Пароли записаны в протоколе Java `Passwords`: PBKDF2-HMAC-SHA256, 600000 итераций, случайная соль 16 байт, результат 256 бит. Значения паролей доступны в fixture только потому, что это публичные учебные аккаунты. При повторной генерации соль и байты файла меняются; состав данных и относительные даты воспроизводятся.

## Генератор и проверка

Для создания ещё одной новой базы с текущей датой:

```powershell
npm run demo:seed -- --output .local/demo-fresh.sqlite3
```

Можно явно задать базовую дату:

```powershell
npm run demo:seed -- --date 2026-10-25 --output .local/demo-fixed-date.sqlite3
```

Без `--output` генератор выбирает `data/demo/preview.sqlite3`. Он также никогда не перезаписывает существующий файл. Для обновления опубликованного образца создайте новый файл, проверьте его, затем осознанно замените старый образец. Не заменяйте им уже используемую базу.

Генератор читает сохранённые SQLite-схемы из `data/demo/sqlite-schema/` и применяет совместимое преобразование `public-listing-details-v2`. Рабочую PostgreSQL-схему создаёт Flyway в `server/src/main/resources/db/migration/`; совместимость образца отдельно проверяется импортёром. При изменении контракта импорта обновляйте генератор и тесты переноса вместе. Проверки включают состав данных, внешние ключи, `PRAGMA integrity_check`, суммы поездок, отсутствие сессий и совместимость хешей паролей.

```powershell
npm run demo:test
```

Тесты также проверяют отказ от перезаписи, запрет путей основной базы, невозможные даты и перенос относительных дат через високосный год. Из SQLite-баз в Git разрешён только один образец: `data/demo/preview.sqlite3`. Все локальные копии, SQLite sidecar и пользовательские загрузки остаются исключёнными.


Резервируйте схему PostgreSQL `demo` вместе с `.local/demo-uploads/`. Копия `.local/demo.sqlite3` не содержит изменений, сделанных в Spring-приложении после импорта.

## Вымышленный диалог отельера

`data/demo/spring-host-dialog.json` — другой, полностью синтетический каталог: две вымышленные гостиницы, две категории и десять учебных утверждений. Он используется только для демонстрации экспериментального диалога `/api/v2/questions/*`; [команды запуска](../server/README.md#вымышленный-диалог-для-демонстрации). Запускайте его в отдельной схеме `host_dialog_demo` с `LAB_MODE=true` и `ACCOUNT_MODE=false`.

Обычные личные уточнения путешественников работают через авторизованные кабинеты и относятся к объявлениям их владельцев. Симулятор v2 не отвечает от имени настоящих гостиниц Пусана. Его JSON явно содержит `demo=true` и `simulated=true`; такие записи не проходят проверенную политику реального каталога.

Результаты актуальной проверки Spring/PostgreSQL и ограничения: [SPRING_MIGRATION_QUALITY.md](SPRING_MIGRATION_QUALITY.md).
