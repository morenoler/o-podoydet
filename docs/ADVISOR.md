# Агентный помощник выбора номера

Помощник встроен в страницу результатов. Его первый сценарий: «Ничего не подошло — объясни причины и помоги найти следующий шаг, сохранив мои обязательные условия».

## Запуск и проверка

### Диалоговый подбор

На странице поиска доступны карта и чат. Переключение сохраняет диалог и список номеров. Сообщения добавляют, удаляют и меняют обязательность условий; обычный `/api/search` пересчитывает подборку. Пример: «рядом с морем» → «ещё тихо» → «тишина обязательна» → «пляж не обязателен». Активные критерии видны над номерами и синхронизированы с ручными фильтрами.

Основная выдача использует `roomRecommendations`: отдельная запись на каждую подтверждённую категорию, где совпали все условия и вместимость. Чат показывает число категорий под условия и число вариантов для уточнения; карточки и источники находятся в основной выдаче. `roomAlternatives` содержит конкретные категории с несовпадениями по желательным условиям или неполными данными; они показаны отдельно и не считаются рекомендациями. `unverifiedHotelCount` считает объекты без подтверждённой категории. Старые `results` и `excluded` сохранены для диагностики. Сведения отельера явно отмечаются; вымышленные категории допустимы только в деморежиме. Наличие на даты и физическая комната не известны.

`POST /api/search/conversation` принимает `{trip, message, focusFeatures}`. Ответ содержит обновлённую `trip`, `message`, `mode`, `warnings`, `focusFeatures` и `changed`. Поле поездки `preferenceOverrides` хранит явные изменения: `{feature, required, enabled}`. Они имеют приоритет над старым свободным текстом, поэтому удалённое условие не возвращается при новом поиске или открытии карточки. Даты, регион и гости не изменяются. Пожелания можно собрать до указания дат.

Обычный поиск и `/api/search/conversation` используют правила либо настроенную модель. Общий выбор AI_PROVIDER=deepseek включает DeepSeek; AI_PROVIDER=rules явно отключает все модельные пути. Тишина относится к признакам внешнего шума и не добавляет условие окон во двор. Неизвестные части запроса явно перечисляются как неприменённые. Местоимение «это» не переносит контекст через нераспознанное пожелание.

Кроме восьми критериев каталога чат меняет `trip.hotelFilters`:

- `query`: «Найди Signiel», «Найди отель Signiel», «Ищи «балкон»», «Хочу номер с балконом», «Нужна кухня», «С бассейном». Это поиск упоминаний в названиях, адресах и исходных описаниях; он не подтверждает удобство или вид для физического номера. Несколько распознанных слов в одном сообщении соединяются как AND. Отрицания удобств автоматически не превращаются в положительные фильтры.
- `lodgingTypes`: «Только апартаменты», «Отели или хостелы», «Любой тип жилья».
- `maxPricePerNight`: «До 100000 KRW за ночь», «Бюджет до 150 тыс вон», «Убери бюджет». Валюта должна быть явно KRW/воны. Применяется указанная цена за ночь; неизвестная цена не проходит лимит. Стоимость и наличие на выбранные даты не проверяются.
- `maxBeachMeters`: «До пляжа 500 м», «До моря 0,5 км», «Убери расстояние до пляжа». Фильтр использует рассчитанную длину пешеходной сети без непроверенных подходов от входа и к воде.
- `nearby`: «В центре города», «Рядом с кафе и рестораном», «Метро до 800 м», «Убери кафе», «Убери всё рядом». У каждого типа свой предел расстояния, обновления объединяются по типу и не стирают остальные условия. Доступны кафе, рестораны, супермаркеты, небольшие магазины, аптеки, парки, метро, музеи, торговые центры, пляжи, железнодорожные станции и выбранный центр Сомён. Все указанные места должны быть в пределах своего радиуса. Это расстояния по прямой, не минуты ходьбы. Альтернативы «или», удалённость и неизвестные названия мест требуют уточнения.

`hotelCandidates` содержит отдельный список реальных объектов карты, у которых ещё не собраны категории номеров. Отображаются только подтверждённые по сохранённым данным совпадения по расположению и источники; вместимость, условия комнаты, цена и наличие не подразумеваются. Этот список не поступает в агентный подбор номеров. Отель с собранными, но устаревшими категориями или неподходящей вместимостью не возвращается через этот список. Поле `nearbyMatches` карточки содержит те же проверенные точки, по которым сервер применил условия.

Точные фразы «Не выше 3 этажа», «На 5 этаже», «Окна на восток» добавляются к `trip.text` и проверяются существующим разбором сведений владельца для одного варианта размещения. Для открытого каталога такие поля могут оставаться неизвестными. Прежние ограничения сохраняются, в том числе несовместимые; чат их не отменяет молча. Сброс отменяет текст, добавленный чатом, если позже его не редактировали вручную.

Запрос на дополнительные свойства за пределами этой грамматики не вызывает модель. Пользователь может явно искать слово в источниках или уточнить условие. `mode` обычного поиска, каталога и чата — `rules`.

История хранится в `sessionStorage` отдельно для пользователя и гостя; настройки поездки сохраняются существующим провайдером. Незавершённое сообщение восстанавливается как черновик. Ответ на уже изменённые условия не применяется. Старый подробный разбор доступен по ссылке «Разобрать найденные варианты» и описан далее; его агенты не используются для изменения фильтров.

Кнопка «Отменить изменения чата» очищает историю, черновик и контекст диалога, отменяет изменения условий из чата и обновляет подборку. Даты, гости, исходный текст и ручные фильтры сохраняются. Для новых фильтров журнал ведётся отдельно по каждому полю; ручное изменение бюджета не мешает отменить добавленное чатом расстояние. Если условие после чата изменили вручную, сброс его не трогает. Журнал изменений фильтров сохраняется локально, поэтому сброс работает и после перезагрузки страницы. Ответ, пришедший после сброса, игнорируется.

### Подробный разбор вариантов

Сервер работает на Java 21, Spring Boot 3.5.6 и PostgreSQL 16. Для помощника нужен Python 3.11+; сторонних Python-зависимостей нет. В `.env` задайте `ADVISOR_PYTHON=python` или полный путь к исполняемому файлу Python. Запустите `npm run dev`, заполните поездку и перейдите к результатам. Нажмите кнопку помощи с выбором. Основной интерфейс использует defaultMode сервера: по умолчанию правила, при явном AI_PROVIDER — выбранную модель. Лаборатория позволяет сравнить модель с правилами.

Для наглядного случая без совпадений включите режим «Только подтверждённые» и выберите «Безопасность района» как обязательное пожелание. В текущем наборе отсутствуют достаточные сопоставимые сведения для подтверждения этого условия. Помощник объясняет нехватку доказательств, не объявляя район опасным. В режиме «Без известных препятствий» допускаются предварительные варианты с provisional=true; предупреждения об обязательных неизвестных условиях сохраняются. Помощник не переключает режим самостоятельно. [Контракт режимов](SEARCH_MODES.md).

Для проверки короткого списка используйте поездку на двух взрослых без дополнительных пожеланий. Помощник покажет категории с подтверждённой вместимостью и оговоркой о непроверенном наличии на даты.

## Роли и границы ответственности

1. Координатор ограничивает объём работы и передаёт агентам общий контекст.
2. Агент потребностей выбирает одно полезное уточнение из проверенных вариантов. Противоречащие пожелания требуют уточнения до рекомендации.
3. Агент подбора выбирает до трёх кандидатов и полезные сценарии из результатов расчётов Java.
4. Агент-критик проверяет, что ограничения и предположения остались видимыми. Модель не может скрыть обязательные предупреждения.

В режиме `rules` эти роли выполняются детерминированным кодом. Это не ответы языковой модели. В режимах `local` и `deepseek` выбор и критика используют два отдельных вызова выбранной модели; проверка идентификаторов и ограничений всё равно выполняется кодом. Ни один режим не изменяет даты, регион, количество гостей, обязательность условий или факты каталога.

Java делает расчёты на одном снимке данных и времени. В обычном поиске контекст имеет `matchingScope: "rooms"`: каждый кандидат связан с конкретной категорией, а все выбранные пожелания должны совпасть в ней. Если точных совпадений нет, Java отдельно рассчитывает последствия удаления одного пожелания. Такие сценарии требуют решения пользователя и не превращаются в текущие рекомендации. Если одного изменения недостаточно, помощник должен прямо это сообщить. Вместимость не ослабляется как компромисс. Демолаборатория сохраняет прежний сценарий оценки отелей по обязательным условиям.

Снимок включает окончательную выдачу после `SearchOverlay`, сведения кабинетов и обезличенные личные уточнения. Новые ответы владельца не меняют уже созданный отчёт. Снимки поиска и запуски помощника доступны только своему пользователю или браузерной сессии.

Пользователь переходит к пожеланиям, вносит выбранные изменения и запускает обычный подбор. Все ссылки на отели и доказательства берутся из серверного контекста. Ассистент не придумывает цены, свободные номера, гарантии безопасности или новые источники.

Если из личного пожелания ничего не распознано, помощник сообщает об этом явно. Выбранные сценарии и фильтры продолжают учитываться, но не выдаются за понимание текста. При частичном распознавании перечисляются только проверенные условия и отмечается, что остальная часть текста не проверена. Внизу карточки объявления отдельно показаны совпадения, несоответствия и условия для уточнения.

## Локальная модель без платы за API

Для воспроизводимой установки Ollama, небольшой модели и копии сайта с визуализацией см. [локальную лабораторию](LOCAL_AI_LAB.md). Можно также использовать собственную установленную локальную модель и указать её точное имя:

```dotenv
ADVISOR_LOCAL_MODEL=имя-локальной-модели
ADVISOR_LOCAL_BASE_URL=http://127.0.0.1:11434/v1
```

После перезапуска Java-сервера локальный режим доступен в лаборатории и API. При пустом AI_PROVIDER основной интерфейс продолжает использовать правила; AI_PROVIDER=local делает локальную модель режимом по умолчанию. Адрес допускается только на loopback, облачные имена моделей запрещены. Для полностью локального Ollama также отключите облачные функции самого сервера. Скорость и качество зависят от модели и оборудования. [Совместимость Ollama с OpenAI API](https://docs.ollama.com/api/openai-compatibility).

DeepSeek поддерживается через AI_PROVIDER=deepseek и серверный DEEPSEEK_API_KEY. Максимум два вызова помощника за запуск, без повторов. При ошибке явно показывается rules_fallback; уже отправленные запросы могли быть оплачены. Ключ не сохраняется в истории. [Полная настройка Java и Python](DEEPSEEK_MODULE.md).

## API и хранение

Обычный `/api/search` возвращает `searchId`. Помощник получает этот идентификатор и использует исходный разбор пожеланий и доказательства именно этой выдачи, без повторного разбора текста и обращения к модели. Сервер хранит максимум 20 снимков на 10 минут. При истечении срока или перезапуске нужно повторить поиск. Интерфейс привязывает отчёт к `searchId` и поездке, показывает время снимка и не подставляет завершённую старую сессию в новую выдачу.

- `GET /api/advisor/config` — доступные режимы без секретов.
- `POST /api/advisor/runs` — `{trip, searchId, mode}`, ответ `202` с заданием.
- `GET /api/advisor/runs` — последние собственные задания.
- `GET /api/advisor/runs/:id` — состояние, контекст, этапы и отчёт.
- `POST /api/advisor/runs/:id/cancel` — отмена с пустым JSON-объектом.

В работе одно задание. Повтор того же активного запроса возвращает существующее задание. История сохраняется в PostgreSQL `advisor_run` с владельцем и регионом. Основной сайт, лаборатория и демо разделены схемами `DB_SCHEMA`; смена активного региона не открывает историю другого региона. После перезапуска незавершённое задание отмечается как прерванное и не запускается заново автоматически. Java ограничивает время Python-процесса и объём JSONL; отмена прекращает процесс. Новая поездка не должна показывать старый отчёт как актуальный.

История и снимки поиска изолированы: у вошедшего пользователя они привязаны к аккаунту, у анонимного — к случайному HttpOnly-cookie браузера со сроком 30 дней. Клиент API должен сохранять cookie между поиском, запуском, опросом и отменой. Чужой идентификатор задания не даёт доступа; чужой снимок нельзя использовать для запуска. В БД хранится хэш анонимного токена. После потери cookie старая анонимная история недоступна. Запуски, созданные до появления владельцев истории, сохраняются в БД с закрытым владельцем `legacy-unowned` и не выдаются публично. При явном `LEGACY_DB_PATH` импортёр переносит владельцев из SQLite `advisor_run_owners` по паре `(region, run_id)`; SQLite не становится рабочим хранилищем.

Смена аккаунта очищает загруженный отчёт интерфейса и создаёт новый поиск. Выход в одной вкладке сообщает остальным вкладкам об изменении сессии. Личные тексты новых уточнений владельцу не передаются в контекст помощника; он получает только публичную проекцию условий. [Контракт уточнений](CLARIFICATIONS.md). Развёртывание в интернете по-прежнему требует отдельной настройки HTTPS, защищённых cookie и эксплуатационных ограничений.

## Проверки

```powershell
npm run agents:test
npm run backend:test
npm test
npm run build:all
```

Тесты модели используют контролируемые ответы, не платный API. `OfflineSearchInterpretationTest` проверяет переход на правила при сбое настроенной модели; структурированные фильтры и однозначные ответы владельца остаются без сетевого вызова. `DeepSeekIntegrationTest` проверяет общий провайдер в Spring, PostgreSQL и настоящем Python-процессе через локальный HTTP-стенд. Тесты чата покрывают новые фильтры, неизвестные валюты, отрицания, смешанные запросы и сброс после ручных изменений. Проверяются отсутствие скрытого ослабления условий, ссылки на реальные кандидаты и доказательства, сохранение предупреждений, отсутствие рекомендаций при противоречиях, лимиты, отмена и восстановление истории. Проверка с установленной локальной моделью проводится отдельно.

Spring-перенос проверяется отдельно на PostgreSQL, включая снимки после пересчёта знаний, владельцев истории и смену региона. Фактический результат текущего прогона и ограничения — в [SPRING_MIGRATION_QUALITY.md](SPRING_MIGRATION_QUALITY.md); прежние отчёты контрактов не заменяют эту проверку.
