# Агентный помощник выбора номера

Помощник встроен в страницу результатов. Его первый сценарий: «Ничего не подошло — объясни причины и помоги найти следующий шаг, сохранив мои обязательные условия».

## Запуск и проверка

### Диалоговый подбор

На главной странице боковая панель открыта сразу. В ней можно переключаться между картой и чатом, сохраняя диалог и список номеров. Сообщения добавляют, удаляют и меняют обязательность условий; обычный `/api/search` пересчитывает подборку. Пример: «рядом с морем» → «ещё тихо» → «тишина обязательна» → «пляж не обязателен». Активные критерии видны над номерами и синхронизированы с ручными фильтрами.

Основная выдача использует `roomRecommendations`: отдельная запись на каждую подтверждённую категорию, где совпали все условия и вместимость. Чат показывает первую такую категорию со ссылкой на неё. `roomAlternatives` содержит конкретные категории с несовпадениями по желательным условиям или неполными данными; они показаны отдельно и не считаются рекомендациями. `unverifiedHotelCount` считает объекты без подтверждённой категории. Старые `results` и `excluded` сохранены для диагностики. Сведения отельера явно отмечаются; вымышленные категории допустимы только в деморежиме. Наличие на даты и физическая комната не известны.

`POST /api/search/conversation` принимает `{trip, message, focusFeatures}`. Ответ содержит обновлённую `trip`, `message`, `mode`, `warnings`, `focusFeatures` и `changed`. Поле поездки `preferenceOverrides` хранит явные изменения: `{feature, required, enabled}`. Они имеют приоритет над старым свободным текстом, поэтому удалённое условие не возвращается при новом поиске или открытии карточки. Даты, регион и гости не изменяются. Пожелания можно собрать до указания дат.

Разбор диалога использует не более одного вызова существующего провайдера `LLM_*`; без него или при ошибке работает ограниченный разбор правилами. Восемь критериев соответствуют каталогу; для неизвестных условий чат явно сообщает, что они не применены. Режим правил не заменяет языковую модель. Тропический душ, бюджет и другие отсутствующие в каталоге характеристики пока не фильтруются через чат.

История хранится в `sessionStorage` отдельно для пользователя и гостя; настройки поездки сохраняются существующим провайдером. Незавершённое сообщение восстанавливается как черновик. Ответ на уже изменённые условия не применяется. Старый подробный разбор доступен по ссылке «Разобрать найденные варианты» и описан далее; его локальные агенты не используются для изменения фильтров.

### Подробный разбор вариантов

Нужен Python 3.11+; сторонних Python-зависимостей нет. В `.env` задайте `ADVISOR_PYTHON=python` или полный путь к исполняемому файлу Python. Запустите `npm run dev`, заполните поездку и перейдите к результатам. Нажмите кнопку помощи с выбором. По умолчанию выбран бесплатный режим правил без модельных вызовов.

Для наглядного случая без совпадений выберите «Безопасность района». В текущем наборе отсутствуют достаточные сопоставимые сведения для подтверждения этого условия. Помощник должен объяснить нехватку доказательств, не объявляя район опасным. Он может показать, сколько категорий прошло бы после удаления этого пожелания, но не должен менять его сам или выдавать исключённые варианты за подходящие.

Для проверки короткого списка используйте поездку на двух взрослых без дополнительных пожеланий. Помощник покажет категории с подтверждённой вместимостью и оговоркой о непроверенном наличии на даты.

## Роли и границы ответственности

1. Координатор ограничивает объём работы и передаёт агентам общий контекст.
2. Агент потребностей выбирает одно полезное уточнение из проверенных вариантов. Противоречащие пожелания требуют уточнения до рекомендации.
3. Агент подбора выбирает до трёх кандидатов и полезные сценарии из результатов расчётов Java.
4. Агент-критик проверяет, что ограничения и предположения остались видимыми. Модель не может скрыть обязательные предупреждения.

В режиме `rules` эти роли выполняются детерминированным кодом. Это не ответы языковой модели. В режиме `local` выбор и критика используют два отдельных вызова локальной модели; проверка идентификаторов и ограничений всё равно выполняется кодом. Ни один режим не изменяет даты, регион, количество гостей, обязательность условий или факты каталога.

Java делает расчёты на одном снимке данных и времени. В обычном поиске контекст имеет `matchingScope: "rooms"`: каждый кандидат связан с конкретной категорией, а все выбранные пожелания должны совпасть в ней. Если точных совпадений нет, Java отдельно рассчитывает последствия удаления одного пожелания. Такие сценарии требуют решения пользователя и не превращаются в текущие рекомендации. Если одного изменения недостаточно, помощник должен прямо это сообщить. Вместимость не ослабляется как компромисс. Демолаборатория сохраняет прежний сценарий оценки отелей по обязательным условиям.

Пользователь переходит к пожеланиям, вносит выбранные изменения и запускает обычный подбор. Все ссылки на отели и доказательства берутся из серверного контекста. Ассистент не придумывает цены, свободные номера, гарантии безопасности или новые источники.

## Локальная модель без платы за API

Для воспроизводимой установки Ollama, небольшой модели и копии сайта с визуализацией см. [локальную лабораторию](LOCAL_AI_LAB.md). Можно также использовать собственную установленную локальную модель и указать её точное имя:

```dotenv
ADVISOR_LOCAL_MODEL=имя-локальной-модели
ADVISOR_LOCAL_BASE_URL=http://127.0.0.1:11434/v1
```

После перезапуска Java-сервера локальный режим появится в помощнике. Адрес допускается только на loopback, облачные имена моделей запрещены. Для полностью локального Ollama также отключите облачные функции самого сервера. Скорость и качество зависят от модели и оборудования. [Совместимость Ollama с OpenAI API](https://docs.ollama.com/api/openai-compatibility).

Платные удалённые провайдеры здесь не поддерживаются. Ключи `LLM_*` не используются помощником. Максимум два модельных вызова за запуск, без повторов; вход и выход ограничены. При недоступной локальной модели помощник явно сообщает о переходе к правилам. Это не переключение на другой API. Счётчики отражают выполненные попытки вызовов и полученные сведения об использовании токенов.

## API и хранение

Обычный `/api/search` возвращает `searchId`. Помощник получает этот идентификатор и использует исходный разбор пожеланий и доказательства именно этой выдачи, без повторного вызова модели. Сервер хранит максимум 20 снимков на 10 минут. При истечении срока или перезапуске нужно повторить поиск. Интерфейс привязывает отчёт к `searchId` и поездке, показывает время снимка и не подставляет завершённую старую сессию в новую выдачу.

- `GET /api/advisor/config` — доступные режимы без секретов.
- `POST /api/advisor/runs` — `{trip, searchId, mode}`, ответ `202` с заданием.
- `GET /api/advisor/runs` — последние задания.
- `GET /api/advisor/runs/:id` — состояние, контекст, этапы и отчёт.
- `POST /api/advisor/runs/:id/cancel` — отмена с пустым JSON-объектом.

В работе одно задание. Повтор того же активного запроса возвращает существующее задание. История сохраняется локально в SQLite `advisor_runs`. После перезапуска незавершённое задание отмечается как прерванное и не запускается заново автоматически. Java ограничивает время Python-процесса и объём JSONL; отмена прекращает процесс. Новая поездка не должна показывать старый отчёт как актуальный.

Это локальный прототип одного пользователя. Правила авторизации для публичного размещения остаются теми же, что у основного приложения.

## Проверки

```powershell
npm run agents:test
npm run backend:test
npm test
npm run build:all
```

Тесты модели используют контролируемые ответы, не платный API. Проверяются отсутствие скрытого ослабления условий, ссылки на реальные кандидаты и доказательства, сохранение предупреждений, отсутствие рекомендаций при противоречиях, лимиты, отмена и восстановление истории. Проверка с установленной локальной моделью проводится отдельно.
