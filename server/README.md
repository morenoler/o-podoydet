# Бэкенд на Spring Boot

Весь API «О!Подойдёт» работает в одном приложении Spring Boot 3.5 (Java 21) на PostgreSQL 16 + PostGIS. Прежний бэкенд (JDK HttpServer + SQLite) полностью перенесён и удалён из репозитория; его ответы сохранены как эталоны в `contract/snapshots/`.

```
Vite :3000 ──→ Spring Boot :8080 ──→ PostgreSQL (docker compose)
                 ├─ ядро знаний: доказательства, факты, противоречия   (ru.opodoydet.server.knowledge)
                 ├─ диалог с отельером                                  (ru.opodoydet.server.host)
                 ├─ поиск: подбор + пересчёт условий по фактам          (ru.opodoydet.server.search)
                 ├─ кабинеты: вход, объявления, фото, заявки, вопросы    (ru.opodoydet.accounts)
                 ├─ оценка района, разбор запроса, подбор               (ru.opodoydet.application, domain)
                 ├─ помощник подбора → Python-воркер agents/             (ru.opodoydet.advisor)
                 └─ раздача собранного фронтенда dist/ и фото /uploads
```

## Как устроен перенос

- **Доменная логика перенесена как есть.** Подбор, оценка района, разбор текста, помощник, кабинеты — обычные Java-классы без зависимости от Spring (`ru.opodoydet.*`). Их собирает `DomainConfig`, а контроллеры Spring (`AccountController`, `PlatformController`, `CatalogController`, `SearchController`) повторяют прежние маршруты, коды ответов и тексты ошибок.
- **SQLite → PostgreSQL.** `AccountDatabase` и `Store` сохранили прежний API, но работают через пул соединений и транзакции Spring. Схема — миграции Flyway (`V1` ядро знаний, `V2` диалог с отельером, `V3` кабинеты, помощник, демо-вопросы).
- **Перенос данных.** `SqliteImporter` при первом старте копирует из прежнего SQLite-файла (`DB_PATH` → `LEGACY_DB_PATH`) аккаунты и сессии, объявления, заявки, вопросы, фото, историю помощника и ответы отельеров. Импорт идемпотентен и выполняется один раз для каждого файла; пароли продолжают работать (тот же PBKDF2).
- **Копии сайта.** Основной сайт, лаборатория и демо работают в одной базе в разных схемах (`DB_SCHEMA`: `public`, `lab`, `demo`).
- **Защита.** `OriginGuardFilter` — та же проверка Origin для изменяющих запросов (`FRONTEND_ORIGIN` для Vite). Сессии — cookie `op_account_session`, как раньше.

## Ядро знаний

Главная идея: мы храним не «поля отеля», а **доказательства**, а факт — вычисляемая проекция из них.

| Таблица | Что хранит |
|---|---|
| `characteristic` | Реестр характеристик: уровень (отель/номер), инструмент, тип значения, срок жизни. Новая характеристика — новая строка (`src/main/resources/knowledge/characteristics.json`) |
| `source_method` | Априорное доверие к методу: official 0.9, geo 0.8, host 0.7, agent 0.5, demo 0 |
| `evidence` | Доказательство: значение, метод, источник и URL, цитата, уверенность источника, даты получения и истечения, исходная запись. Не редактируется — заменяется новой записью через `superseded_by` |
| `fact` | Итог по предмету (отель/номер × характеристика): значение, статус `confirmed / conflict / stale / unknown`, числовая уверенность, срок годности, ссылки на доказательства |
| `conflict` | Журнал противоречий между источниками: открывается и закрывается, но не удаляется |

`Resolution` (чистая функция, см. `ResolutionTest`) превращает доказательства в факт:

1. Отбрасывает недопустимые (демо, без проверяемого источника, из будущего).
2. Срок жизни — `expiresAt` источника, иначе `ttl` характеристики. Все устарели → `stale`.
3. Свежие согласны → `confirmed`, уверенность складывается как noisy-OR (два источника по 0.6 → 0.84).
4. Свежие расходятся → `conflict`: берётся значение с наибольшим весом, уверенность снижается, противоречие пишется в журнал.

Вес доказательства = доверие к методу × уверенность источника (low 0.45, medium 0.7, high 0.9).

`FactResolver` пересчитывает факты после импорта и раз в час (`KNOWLEDGE_RESOLVE_INTERVAL`), поэтому факты сами становятся `stale`, когда у источников истекает срок.

`SeedImporter` при старте загружает `data/verified-hotels.json` с теми же правилами, что старый `Store.importSeed`: повторный импорт идемпотентен, порядок записей сохраняется, заменённые доказательства не перезаписываются.

**Новый API** (`/api/v2`):

- `GET /api/v2/hotels/{id}/knowledge` — факты отеля со статусом, уверенностью и полной цепочкой доказательств, плюс журнал противоречий;
- `GET /api/v2/characteristics` — реестр характеристик;
- `POST /api/v2/knowledge/resolve` — принудительный пересчёт.

Ответы прежнего API (`GET /api/health`, `/api/catalog`, `/api/hotels/{id}` и др.) собираются из этого же ядра в прежнем формате — это проверяет контракт.

PostGIS включается отдельной миграцией вместе с первыми геозапросами; сейчас координаты лежат в `lon/lat`.

## Диалог с отельером

Агент сам находит пробелы в знаниях и спрашивает отельера, а свободный ответ раскладывает по полям.

1. **Планировщик** (`QuestionPlanner`) берёт факты со статусом `unknown`, `stale` или `conflict` по характеристикам, которые отельер знает лучше открытых данных (инструменты `host` и `route`). Приоритет — ценность информации: `(1 − уверенность) × срочность × спрос`, где срочность — противоречие 1.0, неизвестно 0.8, устарело 0.6. В текст вопроса попадает контекст: категория номера, что уже известно, а для противоречия — какие источники и что именно утверждают. Одного предмета касается не больше одного открытого вопроса; на уклончивый ответ повторно не спрашиваем 24 часа (`host.reask-after`), кроме противоречий.
2. **Разбор ответа** (`AnswerExtraction`): если заданы `LLM_API_KEY` и `LLM_MODEL` (OpenAI-совместимый `/chat/completions`, подходит и Ollama через `LLM_BASE_URL`), разбирает LLM; иначе или если LLM ничего не нашла — правила для русского текста. В обоих случаях каждое поле обязано опираться на **дословную цитату** из ответа, иначе отбрасывается. Один ответ может заполнить несколько полей: «во двор окон нет, а до пляжа 50 м без лестниц» → три факта.
3. **Доказательства**: каждое утверждение сохраняется с методом `host`, цитатой и уверенностью (оговорки «кажется», «вроде» → low). Новый ответ отельера по тому же предмету заменяет его прежний ответ (`superseded_by`), история сохраняется.
4. **Пересчёт и разбор противоречий**: факты пересчитываются; вопросы, на которые ответ пришёл попутно, закрываются; при противоречии автоматически создаётся уточняющий вопрос. Расстояния согласны в пределах max(50 м, 25 %): 36 м по карте и «около 50 м» от отеля подтверждают друг друга, и уверенность растёт.

| Эндпоинт | Что делает |
|---|---|
| `POST /api/v2/questions/plan?hotelId=&limit=20` | агент формирует вопросы по самым ценным пробелам |
| `GET /api/v2/questions?hotelId=&status=open` | очередь вопросов (status можно перечислить: `open,answered,unresolved,cancelled`) |
| `POST /api/v2/questions/{id}/answer` `{"text": "..."}` | ответ отельера → что извлечено, факты до/после, закрытые попутно вопросы, уточняющие вопросы |
| `POST /api/v2/host/{hotelId}/simulate` | имитированный отельер отвечает на открытые вопросы (сценарий в `knowledge/simulated-hosts.json`) |

**Сценарий для демо** (PowerShell, при запущенном `npm run dev:spring`):

```powershell
$api = "http://127.0.0.1:8080/api/v2"
# Grand Josun: ответы отеля заполняют пробелы и подтверждают карту
Invoke-RestMethod -Method Post "$api/host/way-843161717/simulate" | ConvertTo-Json -Depth 8
# Shilla Stay: раунд 1 — отель говорит «100 м», карта — 276 м: противоречие и уточняющий вопрос
Invoke-RestMethod -Method Post "$api/host/way-627150752/simulate" | ConvertTo-Json -Depth 8
# раунд 2 — на уточнение отель отвечает «около 250 м»: прежний ответ заменён, противоречие закрыто
Invoke-RestMethod -Method Post "$api/host/way-627150752/simulate" | ConvertTo-Json -Depth 8
# итог в браузере: http://127.0.0.1:8080/api/v2/hotels/way-627150752/knowledge
```

Имитированные ответы помечены в данных (`evidence.simulated`, источник «Имитированный отельер (демо)»). В старом API (`/api/hotels/{id}`) ответы отельера не появляются — там по-прежнему только официальные и геоданные.

## Поиск по знаниям ядра

`POST /api/search` и `POST /api/hotels/{id}/evaluate`:

1. `SearchService` (перенесён из прежнего бэкенда) разбирает запрос (сценарии, текст, противоречия), оценивает условия района (воздух, шум, безопасность), вместимость и добавляет объявления из кабинетов.
2. `SearchOverlay` пересчитывает условия, которые решаются фактами об отеле и номере (`beach_walk`, `step_free_route`, `courtyard`, `step_free_access`, `family`), по доказательствам ядра — **включая ответы отельеров** (`CriterionEvaluator` — перенос `Matching.evaluate`, `DecisionPolicy` — перенос `BinaryDecisionPolicy.decide`).
3. Заново считаются статус и баллы номеров и порядок выдачи (устойчивая сортировка, те же ключи, что в старом коде). Исключение по вместимости, противоречивому запросу или требованиям профиля сохраняется.
4. В критерии, подтверждённые ответом отельера, добавляются поля `sources` и `confidence`; в `trace` — шаг «Знания об отелях». Старый фронт новые поля игнорирует.

Если пересчёт ничего не изменил, ответ остаётся прежним: `SearchOverlayIntegrationTest` прогоняет все эталонные поиски из `contract/snapshots` и сравнивает побайтно.

Пример: обязательное условие «окна во двор» — 0 отелей. После ответа отельера Shilla Stay («Номера Standard Family Twin выходят во внутренний двор») — 1 отель, критерий `match` с `decisionBasis: evidence` и `sources: ["host"]`.

Ограничение: помощник подбора (`/api/advisor`) рассуждает над результатом подбора до пересчёта и ответов отельеров пока не видит.

## Запуск

Нужны JDK 21, Node.js и Docker Desktop. Maven скрипты находят сами в `.local/tools` или в PATH.

```powershell
npm run dev            # база в Docker, Spring на 8080, Vite на 3000
npm start              # собранный фронтенд и API на 8080 (после npm run build:all)
npm run lab:start      # лаборатория на 8081, схема lab
npm run demo:start     # демо на 8082, схема demo (после npm run demo:setup)
npm run backend:test   # тесты (поднимают одноразовый PostGIS через Testcontainers)
npm run db:up          # только база
```

Настройки (`.env` или переменные окружения):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | `8080` | порт API |
| `DATABASE_URL` | `jdbc:postgresql://127.0.0.1:5432/opodoydet?currentSchema=public` | база; если задана, Docker не поднимается |
| `DB_SCHEMA` | `public` | схема копии сайта |
| `DB_PATH` / `LEGACY_DB_PATH` | `.local/busan.sqlite3` | SQLite старого бэкенда для однократного переноса |
| `DATA_PATH` | `data/verified-hotels.json` | набор данных региона |
| `UPLOADS_PATH` | `.local/uploads` | фото из кабинетов |
| `FRONTEND_ORIGIN` | пусто | разрешённый Origin фронтенда, например `http://127.0.0.1:3000` |
| `ACCOUNT_MODE`, `LAB_MODE` | `true`, `false` | кабинеты и лаборатория |
| `LLM_API_KEY`, `LLM_MODEL`, `LLM_BASE_URL` | пусто | LLM для разбора текста и ответов отельеров |
| `ADVISOR_PYTHON`, `ADVISOR_LOCAL_MODEL` | `python`, пусто | помощник подбора |

## Контракт API: проверка, что перенос ничего не изменил

`contract/requests.json` — 85 сценариев: каталог, отели, районы, 15 вариантов поиска, оценка отеля, регистрация и вход, кабинет отельера (фото, объявления, черновик, обновление), публичные объявления, вопросы и ответы, заявки (создание, дубль, подтверждение, отмена), профиль, ошибки доступа и валидации, помощник, неизвестные пути. Значения из ответов (id объявления, заявки, фото) подставляются в следующие запросы.

```powershell
npm run contract:verify   # собрать, поднять Spring на чистой схеме и сравнить с эталонами contract/snapshots/
npm run contract:check    # сравнить уже запущенный сервер :8080 с эталонами
```

Изменяющиеся поля (`id`, даты, `searchId`, UUID) нормализуются; новые поля в ответах разрешены; фото сравниваются по типу и размеру. Осознанные отличия перечислены в `allowChanges` (например, `$.database` в `/api/health`).

Результат переноса: **85/85 совпадают** (сверка двух живых серверов, 26.10.2026), после чего старый бэкенд удалён. Отдельно сверены лабораторный поиск (`/api/lab/search`) и полный прогон помощника — отличаются только время и идентификаторы.

## Что ещё можно сделать после хакатона

- Перевести доменные классы с `JsonNode` на типизированные DTO и репозитории Spring Data.
- Привязать вопросы `/api/v2/questions` к аккаунтам отельеров (сейчас эндпоинты диалога открыты).
- Помощник подбора: учитывать ответы отельеров из ядра знаний (сейчас рассуждает над результатом подбора до пересчёта условий).
