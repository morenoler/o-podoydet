# Бэкенд на Spring Boot

Основной сервер находится в `server/`: **Java 21, Spring Boot 3.5.6, PostgreSQL 16 и Flyway**. Он сохраняет React/TypeScript-клиент, маршруты кабинетов, поиск и Python-помощника из `main`, дополняя их ядром знаний ветки `spring-migration`. Python-сервис оценки вида из окна остаётся отдельным процессом в `services/window-view/`.

Docker Compose использует образ `postgis/postgis:16-3.4`. Расширение PostGIS приложению сейчас не требуется: географические расчёты сохранены в существующих модулях, координаты каталога хранятся в `lon/lat`.

## Модули и границы

- `ru.opodoydet.application`, `domain`, `advisor`, `accounts`: прикладная и доменная логика, которую контроллеры вызывают через собранные в `DomainConfig` зависимости.
- `server/accounts/AccountController`, `server/web/PlatformController`, `server/catalog` и `server/search`: адаптеры Spring MVC с прежними HTTP-контрактами.
- `server/knowledge`: доказательства, вычисленные факты и история конфликтов.
- `server/host`: экспериментальный диалог только с вымышленными объектами лаборатории.
- `accounts/clarifications`: авторизованные личные уточнения по конкретному объявлению, отдельно от публичных вопросов и экспериментального диалога.
- `accounts/persistence/AccountDatabase` и `persistence/Store`: PostgreSQL через пул и транзакции Spring. Рабочего SQLite-сервера нет.

Кабинеты не присваивают владельцам объекты OpenStreetMap. Их предложения участвуют в подборе через `OwnerListingSearchProvider` с указанием происхождения сведений. Закрытые заметки и переписка не передаются модели; она получает обезличенную проекцию условий.

## Хранение и перенос

Flyway создаёт и обновляет схему независимо от включения кабинетов:

| Миграция | Назначение |
|---|---|
| V1 | Каталог и ядро знаний |
| V2 | Экспериментальные вопросы отельеру |
| V3 | Аккаунты, объявления, фото, заявки, публичные вопросы и история помощника |
| V4 | Личные уточнения, версии ответов и поколения области действия объявления |
| V5 | Владелец истории помощника |
| V6 | Активный регион и изоляция истории по регионам |

Основной сайт, лаборатория и демо используют разные `DB_SCHEMA`: по умолчанию `public`, `lab`, `demo`. Скрипт запуска подставляет выбранную схему и в явно заданный `DATABASE_URL`. Фотографии хранятся отдельно от сборок: резервируйте соответствующую PostgreSQL-схему и `UPLOADS_PATH` вместе.

Импорт прежней SQLite включается **только явным `LEGACY_DB_PATH`**. `DB_PATH` не запускает перенос и не выбирает рабочую базу. Импортёр открывает источник только для чтения и использует согласованный снимок; переносит аккаунты, сессии, объявления, фото, заявки, публичные и личные вопросы, версии ответов, поколения области действия и историю помощника. Владелец старого запуска читается из `advisor_run_owners` по `(region, run_id)`. История без установленного владельца сохраняется как `legacy-unowned` и не становится публичной.

Импорт идемпотентен: существующие строки PostgreSQL не перезаписываются. Для старых объявлений без публичных колонок этаж и окна берутся из сохранённого профиля только при вставке новой строки. Повторный перенос не восстанавливает очищенные пользователем значения. Пароли остаются совместимыми с PBKDF2 старого приложения. При совпадении глобального идентификатора у разных регионов или несовпадении области действия факта перенос целиком откатывается: чужой факт не прикрепляется к местному отелю, строки не пропускаются молча. Импорт не переписывает уже изменённые в PostgreSQL цепочки исправлений. При ошибке импортёр сообщает о неудаче в журнале и не записывает маркер успеха.

В кабинетах изменение объявления и ответа блокирует строку предложения. Повторные ключи уточнений сериализуются, проверка версии предотвращает потерю конкурентного ответа. Одновременные подтверждения пересекающихся броней не проходят оба. Чтение составных проекций выполняется в согласованном снимке PostgreSQL.

## Ядро знаний и поиск

`evidence` хранит исходные утверждения с методом, источником, цитатой, датами и происхождением. `fact` — вычисленная проекция со статусом `confirmed`, `conflict`, `stale` или `unknown`. `conflict` сохраняет историю расхождений. Реестр характеристик находится в `src/main/resources/knowledge/characteristics.json`.

`Resolution` отбрасывает недопустимые источники, проверяет сроки и сопоставляет значения. Вес метода и источника влияет на оценку, но числовая уверенность не является вероятностью фактической истинности. При конфликте нельзя выдавать выбранное по весу значение за подтверждённое условие. Демо и симулированные записи не допускаются в проверенной политике реального каталога, даже если одна из меток записана ошибочно.

`SeedImporter` загружает сохранённый набор без сетевого сбора. `FactResolver` пересчитывает факты после импорта и по расписанию (`KNOWLEDGE_RESOLVE_INTERVAL`), применяя политику региона соответствующего отеля.

`SearchService` включает `SearchOverlay` в итоговую выдачу, оценку отеля и снимок помощника. Условия сопоставляются внутри одного номера; разные комнаты не складываются в ложное совпадение. `verified` требует доказательств, `explore` допускает неизвестное только как явно предварительный вариант. Конфликт, известное несоответствие, недостаточная вместимость и противоречивый запрос не обходятся пересчётом знаний.

Помощник использует **окончательный снимок после пересчёта**, включая сведения объявлений и обезличенные личные уточнения. Новые данные не меняют уже созданный снимок. Варианты изменения обязательных условий остаются отдельными предложениями, требующими решения пользователя. Если текст пожелания не распознан, это явно отражается в сообщении помощника.

Публичное чтение ядра:

- `GET /api/v2/characteristics` — характеристики;
- `GET /api/v2/hotels/{id}/knowledge` — факты, источники и конфликты; доказательства содержат метки `demo` и `simulated`.

Изменяющий `POST /api/v2/knowledge/resolve` ограничен лабораторным демо. Все API-ответы, включая ошибки, запрещают кэширование; изменяющие запросы проходят проверку Origin.

## Вымышленный диалог для демонстрации

Экспериментальные `/api/v2/questions/*` не имеют связи с владельцем реального отеля, поэтому разрешены только при `LAB_MODE=true`, политике каталога `demo` и явно вымышленных объектах `demo-*` с `demo=true`. Очередь и чтение отдельного вопроса имеют ту же границу. Для обычных личных уточнений используйте авторизованные `/api/account/clarifications` и `/api/host/clarifications`, описанные в [CLARIFICATIONS.md](../docs/CLARIFICATIONS.md).

Отдельный каталог `data/demo/spring-host-dialog.json` содержит две вымышленные гостиницы, две категории и десять учебных утверждений. Сценарии `src/main/resources/knowledge/simulated-hosts.json` не содержат названий или идентификаторов настоящих гостиниц. Ответы сохраняются с `demo=true` и `simulated=true`.

Планировщик формирует вопросы по неизвестным, устаревшим или конфликтующим условиям. Разбор использует ограниченные правила или настроенный модельный экстрактор; цитаты проверяются по исходному ответу. Это экспериментальное извлечение, а не независимая проверка действительности.

Независимые ответы не затирают друг друга. Исправление заменяет только прежнее утверждение в том же вопросе и с тем же происхождением; другая версия остаётся в истории. Новый ответ на другой вопрос сам по себе не устраняет конфликт. Симуляция не может заменить ручное утверждение, и наоборот.

Из корня репозитория, в отдельном PowerShell:

```powershell
npm run backend:build
$env:PORT = "8085"
$env:DB_SCHEMA = "host_dialog_demo"
$env:DATA_PATH = "data/demo/spring-host-dialog.json"
$env:LAB_MODE = "true"
$env:ACCOUNT_MODE = "false"
$env:LEGACY_DB_PATH = ""
$env:LLM_API_KEY = ""
npm start
```

При собственном PostgreSQL также задайте `DATABASE_URL`, `DATABASE_USER` и `DATABASE_PASSWORD`. Не используйте рабочую схему для этого каталога. В другом терминале:

```powershell
$demoApi = "http://127.0.0.1:8085/api/v2"
Invoke-RestMethod -Method Post "$demoApi/questions/plan?hotelId=demo-harbor&limit=20"
Invoke-RestMethod -Method Post "$demoApi/host/demo-harbor/simulate" | ConvertTo-Json -Depth 8
Invoke-RestMethod "$demoApi/hotels/demo-harbor/knowledge" | ConvertTo-Json -Depth 8
```

Для `demo-dunes` первый раунд показывает расхождение 100 м и 276 м. Ответ 250 м в другом диалоге сохраняет конфликт с прежними 100 м. Для вручную введённого ответа повторный `POST /api/v2/questions/{id}/answer` с исправленным текстом заменяет версию того же вопроса. Ручной ответ на вопрос симулятора имеет другое происхождение и не затирает симуляцию. История сохраняется. Остановка сервера — `Ctrl+C`.

## Запуск приложения

Нужны JDK 21, Node.js 24+, Maven 3.9+ и PostgreSQL 16. Без собственного `DATABASE_URL` скрипты поднимают базу через Docker Compose. Maven и JDK могут находиться в `.local/tools` или стандартном окружении.

```powershell
npm ci
npm run dev            # PostgreSQL, Spring :8080, Vite :3000
npm run build:all      # сборка клиента и JAR; не заменяет прогон тестов
npm start             # готовая сборка и API :8080
npm run lab:build
npm run lab:start     # :8081, отдельная схема lab
npm run demo:setup    # один раз создаёт новый учебный SQLite-образец
npm run demo:start    # :8082, явный импорт образца в схему demo
```

| Переменная | Назначение |
|---|---|
| `PORT` | Порт API, обычно `8080` |
| `DATABASE_URL`, `DATABASE_USER`, `DATABASE_PASSWORD` | Собственный PostgreSQL; при заданном URL Docker не запускается |
| `DB_SCHEMA` | Схема копии; по умолчанию `public` |
| `LEGACY_DB_PATH` | Явный источник импорта SQLite; по умолчанию отсутствует |
| `DATA_PATH` | Каталог, обычно `data/verified-hotels.json` |
| `UPLOADS_PATH` | Фотографии, обычно `.local/uploads` |
| `ACCOUNT_MODE`, `LAB_MODE` | Кабинеты и лабораторные возможности; независимо друг от друга |
| `LAB_DB_SCHEMA`, `DEMO_DB_SCHEMA` | Схемы лаборатории и кабинетов демо |
| `LAB_LEGACY_DB_PATH` | Отдельно выбранный источник переноса для лаборатории |
| `FRONTEND_ORIGIN` | Разрешённый Origin Vite; на одной origin не требуется |
| `WINDOW_VIEW_URL` | Адрес отдельного Python-сервиса вида из окна |
| `LLM_API_KEY`, `LLM_MODEL`, `LLM_BASE_URL` | Необязательный разбор поискового текста / экспериментальных ответов |
| `ADVISOR_PYTHON`, `ADVISOR_LOCAL_MODEL` | Python и локальная модель помощника; режим правил работает без модели |

## Проверки

```powershell
npm run backend:test
npm run agents:test
npm test
npm run demo:test
npm run build:all
npm run lab:build
```

Java-тесты используют настоящий PostgreSQL: Testcontainers либо явно заданные `TEST_DATABASE_URL`, `TEST_DATABASE_USER`, `TEST_DATABASE_PASSWORD`. Каждый экземпляр тестового приложения получает отдельную случайную схему; рабочие данные и пользовательские загрузки не используются. Проверяются HTTP, приватность, конкурентные записи, импорт SQLite, история после перезапуска, итоговый снимок поиска и лабораторные ограничения.

`contract/requests.json` и `contract/snapshots/` содержат 85 эталонов, заново снятых с отдельной проверенной сборки актуального `main` e4faa2d; [происхождение эталонов](../contract/README.md). `npm run contract:verify` сравнивает Spring с ними в отдельной схеме. Личные уточнения, конечный снимок помощника и конкурентные операции дополнительно проверяются интеграционными тестами. Фактические результаты и ограничения: [SPRING_MIGRATION_QUALITY.md](../docs/SPRING_MIGRATION_QUALITY.md).
