# О!Подойдёт

## Работа с проектом

- Основное приложение — React/TypeScript + Java 21, Spring Boot 3.5.6 и PostgreSQL 16.
  Сохранять точные версии Java и Spring Boot из `server/pom.xml`, без обновления по ходу других задач.
- `services/window-view/` — отдельный Python 3.11+ сервис; стандартная библиотека,
  запуск и проверки без обязательных внешних зависимостей.
- Пользователь разрешил субагентов. Разделять владение файлами; интеграцию проверяет основной агент.
- Проверять каждый значительный этап; исправлять найденные ошибки до зависимых изменений.
- Перед сдачей запускать существующие тесты/сборку и расширенную проверку нового сервиса.

## Достоверность

- Расчёт видимости — геометрическая оценка по ограниченным данным, не фотография и не подтверждение на месте.
- Неизвестные окно, этаж, направление, высота препятствия и рельеф не превращать в подтверждённый вид.
- Категория номера и оценка отеля не подтверждают вид из конкретного физического номера.
- Хранить источник, дату получения, известную дату исходных данных, метод и допущения.
- Реальные открытые данные и синтетические тестовые сцены разделять. Не выдумывать номера реальных гостиниц.
- Кэшировать открытые источники; сохранять запрос, SHA-256 и атрибуцию. Обычные тесты работают без сети.
- Запросы к публичным источникам ограничивать по времени, объёму и частоте. Не обходить ограничения доступа.
- Не отправлять сообщения отельерам, не публиковать ключи и персональные переписки.

## Проверки

- Приложение: `npm test`, `npm run backend:test`, `npm run agents:test`, `npm run build:all`, `npm run lab:build`, `npm run demo:test`.
- Микросервис: из `services/window-view` — `python -m unittest discover -s tests -v`.
- Расширенная проверка: из `services/window-view` — `python verify_busan.py --workers 4`; 288 запросов по 96 объектам.
- Парсер шумового отчёта: `python -m unittest discover -s scripts/tests`.
- Качество алгоритма, полнота источников и проверка на месте — разные показатели.

## Интеграция

- Весь действующий Java API находится в `server/`. HTTP — контроллеры Spring MVC в
  `ru.opodoydet.server`, сборка доменных компонентов — `DomainConfig`, зависимости передаются
  через конструктор. Сохранять стиль существующих пакетов, Java records для небольших DTO и
  обычные классы application/domain для правил. Не возвращать JDK HttpServer и второй Java API.
- Доступ к PostgreSQL — существующие Spring Data JPA/JdbcClient и TransactionTemplate.
  Изменения схемы — новые последовательные миграции Flyway; применённые V1–V3 не редактировать.
  Многопоточные операции проверять на PostgreSQL: synchronized не заменяет транзакции и блокировки.
- Кабинеты используют таблицы account_*. Проверки получают отдельную временную схему PostgreSQL
  и UPLOADS_PATH. `DB_SCHEMA` разделяет public/lab/demo; не перезаписывать рабочую БД или образец.
  SQLite поддерживается только как источник явного импорта `LEGACY_DB_PATH`, открываемый для чтения.
  Не включать автоматический импорт произвольного прежнего `DB_PATH`.
- Интеграционные тесты используют PostgreSQL 16 через Testcontainers либо TEST_DATABASE_URL,
  TEST_DATABASE_USER и TEST_DATABASE_PASSWORD. Не подменять PostgreSQL SQLite/H2 и не пропускать
  проверки молча при недоступном Docker. После получения образов и зависимостей тесты не требуют
  внешних API и ключей. Java запускать только на JDK 21; сборка — Maven через scripts/backend.mjs.
- Основной каталог использует verified-only источники; режим допуска поиска задаётся отдельно.
  Синтетическая лаборатория работает на 8081 со своей схемой PostgreSQL. Имитация отельера разрешена
  только для вымышленных объектов демокаталога, помечается demo/simulated и не подтверждает реальные отели.
- API сохраняет evidenceStatus: неизвестность не становится подтверждённым фактом. В режиме explore неизвестные обязательные условия допускаются только как provisional; установленное несоответствие или конфликт исключают. Режим verified требует подтверждений. UI различает эти состояния и не называет неизвестную безопасность подтверждённой.
- Личные уточнения находятся в `accounts/clarifications`, отдельно от публичных вопросов. В поиск и модель передавать только обезличенную проекцию условия; не передавать текст переписки, пользователя, идентификатор диалога или чужой исходный запрос.
- Структурированный ответ владельца относится только к варианту одного объявления. Разрешены family, courtyard, step_free_access; ответ не подтверждает район или маршрут. Новые версии сохраняют историю, конфликт разных диалогов требует явного исправления.
- Положительное условие должно покрывать всю поездку; отрицательное учитывается при пересечении дат, включая выезд. Устаревшие и неизвестные сведения не восстанавливают старое подтверждение. Смена материальных параметров объявления инвалидирует старую область действия даже после возврата прежних значений.
- Снимки поиска и история помощника имеют владельца. HTTP-клиент проверки должен сохранять cookie между поиском, запуском и чтением результата; чужой searchId/runId не даёт доступа.
- По умолчанию публиковать изменения в отдельную ветку. Слияние и публикация в main разрешены по явному поручению пользователя; сохранять изменения обеих веток, перед публикацией проверять актуальный main и регрессии. Не использовать force push.
- При запущенной пользовательской демоверсии собирать интерфейс в `.local/` и проверять на отдельной БД/порту. Во время обновления живой сборки сохранять старые хешированные assets для уже открытых вкладок; пользовательскую БД и загрузки не заменять тестовыми.

- Материалы дизайн-аудита, скриншоты и вспомогательные инструменты хранить только в игнорируемых `.local/` или `.impeccable/`; не включать их в коммиты.
