## Что изменилось относительно прежнего эталона

Старые 85 снимков сохранены без изменения ответов в `legacy-snapshots/`, их манифест — `legacy-manifest.json`. Они происходят от main `e4faa2dbc006a1a785e43059c83d10a5c239f084`, сняты 26.10.2026 с прежнего SQLite-бэкенда; SHA-256 того JAR: `b04b8752c9745a985ae8847bad6961ddd72f0be692ea1b811b0e83faf19a1c4e`.

Два старых запроса создания/обновления опубликованного объявления перестали соответствовать обязательным полям main. В них добавлены три спальных места: одна двуспальная и одна односпальная кровать. Координаты оставлены неизвестными (`null`); остальные исходные значения сохранены. Это устраняет каскад из 21 ошибочного сценария после неудачного создания объявления.

При повторном снятии с исходного main все **85 HTTP-статусов** совпали с прежними ожидаемыми. Помимо ранее разрешённых отличий SQLite→PostgreSQL и новых полей, подтверждены ровно четыре изменения существующих данных:

| Сценарий | Поведение исходного main |
|---|---|
| `search-text` | Актуальный порядок разобранных условий и предупреждения о непонятой части запроса |
| `search-text-conflict` | Просьба о тишине больше не подтверждает окна во двор; используется условие внешнего шума |

Эти отличия воспроизведены на исходном коде main; ответы исправляемой ветки не использовались для обновления эталона.

## Проверка

```sh
npm run contract:verify
```

Команда собирает сервер, проверяет свободность порта 8089, создаёт уникальную PostgreSQL-схему `contract_*` и отдельную папку загрузок. Она включает кабинеты, отключает лабораторию, модели и импорт учебных кабинетов. Данные берутся из сохранённых файлов репозитория независимо от пользовательских путей в `.env`. После проверки процесс останавливается; схема и файлы запуска остаются для разбора.

Для отдельного PostgreSQL задайте `DATABASE_URL`, `DATABASE_USER`, `DATABASE_PASSWORD`; иначе используется Compose. Не запускайте проверки на рабочем экземпляре: сценарии создают вымышленные аккаунты, объявления, фото и заявки.

Профиль Spring `contract` получает `Clock` из `baseline.json.clockInstant`, то есть времени начала эталонного прогона. Исходный main снимался со своим системным Clock в течение 11 секунд; его код не изменяли и тестовую замену Clock в него не внедряли. UUID и изменчивые времена нормализуются. Обычное приложение продолжает использовать настоящее время, сроки источников не продлеваются.

Для прямого сравнения двух независимо запущенных серверов:

```sh
node scripts/contract.mjs diff --base http://127.0.0.1:8088 --against http://127.0.0.1:8090
```

Обе копии должны иметь одинаковые входные наборы, согласованное время, пустые независимые схемы и собственные каталоги загрузок. Повторный прогон на той же схеме изменяет исходное состояние; для сравнения нужен новый экземпляр схемы.

## Хранение и ограничения

Крупные ответы хранятся в `.json.gz`, небольшие — читаемым JSON. Текущий набор занимает 1 160 700 байт, архив прежнего — 863 249 байт вместо исходных 19 477 232 байт несжатых старых эталонов. `snapshots-manifest.json` и `legacy-manifest.json` описывают размер и SHA-256 распакованных ответов; тест проверяет оба набора по 85 файлов.

`requests.json` сохраняет точечные `allowValueChanges` из истории миграции, а не пропуск целых объектов `trace`. Сравнение разрешает новые поля, но выявляет удаление старых полей и изменение их значений. `capture` выполняется явно и отклоняет сетевые ошибки и HTTP 5xx; успешная команда сама по себе не подтверждает правильность каждого ответа. Поэтому при переснятии отдельно сверены все статусы и изменения существующих полей.

Это проверка контракта HTTP на сохранённых данных. Она не подтверждает фактическое состояние гостиниц, полноту источников или доступность маршрутов на месте. Приватность, конкурентные изменения, новые доказательства и атомарность дополнительно проверяются тестами PostgreSQL.
